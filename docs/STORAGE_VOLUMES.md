## Public API and integration contract

`src/storage_volume.rs` has no database dependency or mutation API. The parent catalog exposes it with `pub mod storage_volume;`; the isolated tests currently include it by path. Existing `serde`, `uuid`, and `libc` dependencies suffice. No build script changes or new packages are required.

- `LogicalVolume::new(optional_os_identity)` generates a catalog UUID once. Persist and reuse this UUID across remounts and explicitly approved replacement-drive mappings; never regenerate it from a label, path, or OS UUID. Multiple logical registrations are not automatically merged because their OS IDs match.
- `NativePath` serializes Unix bytes or Windows UTF-16 units without a Unicode conversion. A foreign-platform encoding remains representable but cannot become a local path without explicit remapping. Embedded NUL is rejected on conversion. UI display strings must never be used as authoritative paths.
- `locate(absolute_path)` observes existence, canonical target, actual mounted filesystem, optional persistent identity, and a verified relative path inside that filesystem. It rejects relative paths, parent traversal, Windows device namespaces, and special filesystem objects. Symlink/junction aliases are resolved to their existing target. Requested and canonical object identities are checked before and after the observation. `Available` means the filesystem object exists at the time of observation, not that its content matches a catalog asset or that its volume has a persistent ID.
- Missing requests remain `MissingPath`, with requested `volume`, `canonical_path`, and `relative_in_volume` absent. A separate `existing_ancestor` records the longest accessible existing directory, its verified mount, and an **unresolved lexical suffix**. For a disconnected `/Volumes/OldRaid/Raw/photo.cr2`, this ancestor may be on the boot disk. Its volume must never be assigned to the missing photo or treated as proof that the photo is available. Errors or special objects encountered while finding an ancestor stop the search.
- `mounted_volumes()` returns a bounded snapshot and explicit issues. `complete=false` means enumeration was truncated, failed, or encountered uncertain identity lookup; absence is then indeterminate. `complete` is not a guarantee of an atomic OS snapshot or an identity for every filesystem.
- `match_mounts(logical_volume, snapshot)` returns `IdentityUnavailable`, `Offline`, `Indeterminate`, `Unique`, or `Ambiguous`. It compares typed persistent IDs only. All duplicate observations, including mount aliases and bind mounts, stay ambiguous. It never breaks ties using labels, old mount paths, device numbers, or enumeration order. `Offline` means that the identity was not observed in a complete snapshot; it does not prove physically unplugged hardware.
- `candidate_path(mount, relative_in_volume)` performs a pure, traversal-checked mapping, respecting a Linux mounted subdirectory. It does not check existence or bypass relink content verification. Re-probe a candidate immediately before the catalog transaction and verify the catalog's source/content evidence. A mount change or directory reorganization must never erase stable asset/edit identities.

Snapshot issues and absent relative mappings must remain visible to the caller. This code never guesses a missing persistent identity from a mount path, volume label, serial number, mount ID, or device number. An explicit user-selected replacement drive can have a new OS identity while retaining the logical catalog UUID; the catalog must record that choice and provide undo.

## Platform implementations

| Platform | Persistent identity | Actual mapping and limits |
| --- | --- | --- |
| macOS | `kCFURLVolumeUUIDStringKey`, normalized UUID, nullable | `statfs` identifies the actual mounted filesystem. The UUID is queried on that mount's URL. A lexical relative path is used when available. For APFS firmlinks, a possible physical alias under the returned mount is accepted only when device/inode and filesystem ID match. Failure leaves `relative_in_volume=None`; no boot-volume substitution or hardcoded `/Users`/volume-name rule. `getfsstat(MNT_NOWAIT)` reads the cached mount list, bounded to 4,096 entries. |
| Windows | Local mount-manager volume GUID, normalized UUID | `GetVolumePathNameW` and `GetVolumeNameForVolumeMountPointW` map existing canonical paths. A metadata-only handle and `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` provide the actual volume-relative suffix, including mounted-folder/junction targets. `GetFileInformationByHandleEx(FileIdInfo)` checks the 128-bit object ID and current volume serial, used only for observation consistency. GUID enumeration includes all reported mount aliases. Strings are bounded to 32,768 UTF-16 units and snapshots to 4,096 volumes/mount paths. |
| Linux | Filesystem UUID names in `/dev/disk/by-uuid`, bound through block-device metadata | `/proc/self/mountinfo` supplies current device pairs, component mount paths, and internal roots for bind mounts/subvolumes. The deepest matching mount on the observed device wins; stacked indistinguishable mountpoints fail explicitly. The parser retains escaped/non-UTF8 paths. Device and transient mount IDs are never persisted as stable identity. Mountinfo is bounded to 4 MiB/4,096 entries; UUID entries to 4,096. No raw block-device reads or external command invocation. |

The macOS property explicitly permits no UUID. Network filesystems, virtual filesystems, permissions, unavailable udev links, and filesystems whose mount device cannot be associated with a block UUID (including some Btrfs/multi-device configurations) can therefore have an available path and an unavailable persistent identity. These are explicit manual-relink cases, not automatic reconnection evidence. Linux support does not claim to discover UUIDs that udev has not exposed.

Windows SMB/UNC shares have no local mount-manager GUID. Their existing paths may provide a canonical relative mapping with `persistent_identity=None`; they always need explicit mapping. If the filesystem cannot provide a reliable file-handle identity, observation fails explicitly rather than using length/timestamps as identity. The local GUID enumeration does not enumerate arbitrary network shares. Windows may expose more than one GUID name for one volume; the API returns its first cached mount-manager name. This is a host-local reconnect hint, not a portable global disk identity.

Cloned filesystems may duplicate UUIDs. Visible duplicate observations are ambiguous; a hidden/offline clone or a collision suppressed by one `/dev/disk/by-uuid` symlink cannot be discovered from this bounded interface. Independently verify content and retain ambiguity review at the catalog layer. Reformatting or replacing a filesystem legitimately changes its identity. OS observations are not an atomic mount lock: final checks catch ordinary replacements, but a concurrent unmount/remount or namespace ABA race still requires fresh catalog commit-time validation.

Calls on unresponsive remote filesystems can block in OS metadata APIs. Run this synchronous adapter in the existing cancellable worker/process boundary, not the UI thread; it does not promise kernel-level cancellation or recursively probe mounted volumes. Unix never opens selected filesystem objects; Windows opens existing regular files/directories with requested access zero for handle metadata only.

## Primary API references

- Apple's [volume UUID resource key](https://developer.apple.com/documentation/corefoundation/kcfurlvolumeuuidstringkey?language=objc) documents nullable persistent UUIDs. Darwin's [statfs declaration](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/mount.h) supplies mount fields and filesystem IDs.
- Microsoft's [volume path lookup](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamew) can succeed for nonexistent trailing path components, which is why existence is checked separately. [Mount-point GUID lookup](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumenameforvolumemountpointw) documents GUID aliases and network limitations.
- Microsoft's [mount-path enumeration](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamesforvolumenamew), [handle path lookup](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), and [128-bit file identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) define the Windows evidence used here.
- Linux [mountinfo](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html) defines mount roots, device pairs, escaping, and reusable mount IDs. systemd's [persistent storage udev rules](https://github.com/systemd/systemd/blob/main/rules.d/60-persistent-storage.rules.in) establish `disk/by-uuid` links from filesystem UUID properties.

Confidence: high for the tested macOS read-only identity, firmlink, and disposable remount behavior; medium for cross-platform behavior until native Windows/Linux CI and the parent catalog integration pass. Snapshot/race and missing-identity limits above remain part of the API contract.
