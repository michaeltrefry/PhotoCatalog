# Storage identity and relinking

S5 stores a logical catalog volume UUID separately from an operating-system volume identity. Labels, mount names, drive letters and basename matches are never identities. Originals and sidecars are opened read-only. Relinking and undo change catalog references only; they do not move, write or delete original files.

`storage_volume` supplies lossless paths and platform observations. The importer supplies `bind_storage` with the verified file's available volume observation. Repeated identical binding changes neither the storage revision nor render generation. Before reserving an import at a new path, `reconnect_storage_asset` uses the indexed persistent-volume identity and volume-relative path to find an existing identity, checks the import's complete content digest, and executes an ordinary persisted relink. Known ambiguity and changed content return errors; they are not permission to reserve a duplicate. The importer supplies a cached mount snapshot; reconnect requires it to be complete with one matching mount before changing a known asset path. Duplicate/indeterminate identities require explicit review. New imports and unchanged-location reimports do not depend on mount-enumeration uniqueness. Paths on storage without persistent identity remain available for explicit mapping.

Every S5 binding stores the current native locator's encoding separately from a logical legacy path reference. Catalogs can therefore retain Windows UTF-16 paths while opened on macOS/Linux, or Unix byte paths while opened on Windows. Each source also retains an independent current locator tag: an excluded foreign sidecar keeps its own encoding after its asset moves to another OS. Apply seals unknown source encoding explicitly rather than later inheriting a new asset encoding; matched remaps and undo compare and restore source tags atomically. Source-locator readback and remapping use those tags. They never reinterpret foreign bytes as a host path. New imports call `record_storage_path` even if volume identity lookup fails. Untagged v1/v2 locations remain `Unspecified` until the caller explicitly declares their origin with bounded, resumable `declare_storage_encoding` batches (CLI `declare-storage-encoding unix|windows --after <sequence> --limit <1..1000>`); the display string is never used to guess encoding. Explicit file relinks can still verify a supplied candidate by full digest, with separate sidecar choices when its old locator is unspecified.

`storage_status` reports offline, missing, ambiguous, indeterminate and identity-unavailable states without removing assets, previews, metadata, or organization. An online candidate is explicitly unverified until content validation. Missing paths are not attributed to the ancestor's volume.

## Review and publication

1. `begin_relink` records a prefix, individual-asset, or known-volume request plus a catalog storage revision and asset high-water mark. Prefixes can use native paths or explicitly tagged old Unix/Windows references. Components compare exactly; Unicode normalization and filename case guesses are not performed. Windows slash/backslash and extended filesystem path spellings are supported. Dot components, NULs, device namespaces and paths that cannot be represented losslessly on the destination platform are refused.
2. Add per-asset or per-sidecar candidate exceptions before preparation. These are database rows, not a growing in-memory dictionary. A maximum of 32 explicit alternatives is accepted per item; an empty exception means explicitly retaining its old locator. Embedded source locators always follow their original and cannot be independently excluded or redirected.
3. `prepare_relink_batch` scans at most 1,000 catalog assets per call using sequence cursors. Prefix plans do not recursively scan destination trees: they construct descendants by the exact relative suffix. Each candidate is hashed in bounded 64 KiB buffers. Missing, different-content, inaccessible and multiple matching candidates remain visible. Same-name content mismatches are never matches. Symlinks, nonregular files and catalog-managed destinations (including cached previews) are refused. File identity, length and modification time bracket the hash read.
4. `relink_items` and `relink_sources` expose bounded pages. An unresolved original or source prevents apply unless explicitly excluded. Excluded items retain all prior references and evidence. Correct a mapping by creating a new plan; old failed or abandoned plans remain reviewable.
5. `apply_relink` takes one SQLite IMMEDIATE transaction, checks the plan's storage revision and each original's metadata/render revision, verifies destination bytes and file identity again, and checks destination collisions. Updates use temporary internal BLOB keys so valid swaps do not violate uniqueness midway. Current embedded/verified-sidecar locators keep their source IDs and observations. Immutable `source_location` provenance, packets, model IDs, selections, asset IDs and preview references remain intact. A byte-identical source with a changed locator or timestamp retains its model and explicit choices; new file-instance provenance is recorded separately, including timestamp-only changes and copies replacing the same path. Full file bytes, extraction provenance, packet layout and parser/model evidence must still match. Actual original path changes advance render generation and metadata revision, making older render/export plans stale. A final streamed content check precedes commit.
6. `undo_relink` uses the retained old rows in one transaction. It restores old paths and current source locators even if the old volume is offline. It never restores an earlier metadata value over a user's edit or decrements generation counters. Per-asset applied-state and source-observation checks reject intervening changes to affected originals or edits; unrelated imports do not invalidate undo. Per-asset relink lineage permits reverse-order undo. Only revision increments produced by a verified newer undo can advance the preceding operation's undo guard; an independent edit cannot be hidden by applying and undoing another relink. Old-path collisions also refuse undo. Repeated apply/undo of an already completed operation is idempotent.

Plan creation and each preparation batch are independently durable. A process interruption while applying or undoing rolls back all path/source changes through SQLite WAL recovery. No intermediate temporary path is committed. A missing identity or relative-path result never erases an existing stable binding merely because a native query was temporarily incomplete. Plans survive restart and are paginated on disk; memory does not grow with the number of assets or files in a mapping. A large atomic relink occupies the catalog writer while performing full verification, so callers should schedule it as a background storage operation and make cancellation return an error before commit. Reader browsing can continue through WAL snapshots.

The filesystem and database do not share a transaction. The evidence means that the full bytes and object identity matched at the final observation, not that external applications cannot change a file after validation. No filesystem compare-and-swap or continuous storage availability is claimed. Durability relies on the catalog's existing WAL/FULL/fullfsync settings and the filesystem honoring synchronization.

## Validation boundary

Disposable tests cover offline browsing, known-volume reconnection, nested/Unicode and non-UTF8 names, explicit old Windows/Unix mappings and simulated cross-OS catalog/source transport, exact prefix boundaries, missing and wrong-content paths, duplicate candidates/destination collisions, single-file exceptions, sidecar source/provenance retention, stale plans, replacement after preview, transactional fault injection, restart and undo. Fixtures simulate volume removal by renaming disposable directories; they never detach the user's RAID. Actual operating-system volume adapter tests and final three-platform CI are separate required integration evidence. Full Lightroom catalog-family inspection and migration remain their own approved stories; this API accepts explicit legacy references without claiming that import is implemented here.
